# Stack Blueprint — Design Contract

## Product context

Stack Blueprint is the first consultation at the start of any software project. A builder describes one idea; the browser agent infers the project profile, consults a comprehensive decision taxonomy, VibeLeaderboard's public tool survey, and current Intel, then draws both the production stack and AI-building toolkit automatically. The memorable thing is: **a connected tree of specific tool logos draws itself one pick at a time while the architect explains what it is adding.**

Audience: technical and AI-assisted builders choosing a new project's architecture, services, developer tools, and agent workflow. They want a decisive, researched answer first and optional education second.

## Aesthetic direction

A clean specification sheet, not a SaaS dashboard and not retro blueprint cosplay. Light, direct, precise, and visibly under construction. Blueprint connection diagrams inform the structure; no source is copied visually.

Decoration level: low. Every line denotes structure, state, measurement, or hierarchy.

## Typography

- Barlow Condensed: upright display, section titles, tool names, and the wordmark.
- IBM Plex Mono: labels, controls, annotations, and explanatory copy.
- Tabular numerals everywhere. Uppercase tracking only for labels.
- No italic wordmark, serif display face, or system font.

## Color

- Drawing field: pale cool paper with a restrained dot grid.
- Primary linework: cool grey and specification blue.
- Reading surface: white.
- Ink: near-black blue.
- One signal color: construction blue.

Construction blue is reserved for the primary kickoff action, active drawing lines, progress, and inspect affordances. It is never decorative.

## Content encoding

- The decision system must cover the practical categories in a complete modern software stack plus the AI tools used to research, design, implement, review, test, and ship it.
- The visible answer must name specific implementations rather than abstract categories such as “versioned skill library” or “routed builder.”
- The architect chooses automatically after consulting the public tool survey and Intel. The user is not asked to operate a comparison flow.
- The AI build branch must name a coding harness, current builder model, exact frontend/backend/database/verification skills, CI, and research source.
- Each logo opens a focused explanation with its role, rationale, and official source. Alternatives appear only when explicitly requested.
- Any layer may be explicitly omitted when it does not serve the project. Comprehensive coverage must not become forced complexity.
- No transcripts, article bodies, private data, vanity inventory totals, or invented performance scores.

## Layout

- Composition: masthead, one-question brief, narrator strip, project root, and three connected branches—product stack, connected services, and AI build setup.
- Tool nodes contain a logo, name, and quiet grey category label. The overview never exposes explanatory paragraphs or option grids.
- Rationale and provenance live in the on-demand tool inspector.
- Borders and connecting lines are structural. Shadows appear only behind the focused inspector.

## Motion

- Tool nodes arrive one at a time on a 560ms cadence. Structural lines draw with transform-only motion.
- The narrator names and briefly reviews each tool as it is placed.
- Never animate text while it is being read.
- Reduced motion preserves the reveal hierarchy with near-instant transitions.

## Mobile

- One column, no horizontal scrolling.
- Option grids stack; every action is at least 44px high.
- The connected branches become one vertical sequence.
- The inspector becomes a bottom sheet.

## Anti-patterns

No comparison grids, alternative cards, dense explanatory copy in the overview, blobs, grain, faux 3D, duplicate calls to action, or screenshot-shaped fake previews.
